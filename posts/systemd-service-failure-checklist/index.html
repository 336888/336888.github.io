systemd 服务起不来，怎样找到首个报错

联查服务状态、日志和生效配置，避免被重启限流掩盖根因。

把下面的 myapp.service 换成实际服务名。先保留失败现场，再决定是否重启。

systemctl status myapp.service --no-pager --full
journalctl -u myapp.service -b -n 100 --no-pager
systemctl cat myapp.service

从最后一次启动往前看

如果日志最后写着 Start request repeated too quickly，继续往前找第一次退出的原因。203/EXEC 时核对可执行文件路径、执行权限和脚本解释器。退出码来自应用本身时，优先看应用写出的配置或依赖错误。

核对服务实际用的配置

systemctl cat 会列出 unit 文件和 drop-in。重点检查 ExecStart、User、WorkingDirectory 和 EnvironmentFile。手动能运行但服务失败时，比较两个环境中的用户权限、工作目录和环境变量。

修完后验证运行状态

如果修改了 unit 或 drop-in，先执行 sudo systemctl daemon-reload。如果已经触发启动限流，修复原因后执行 sudo systemctl reset-failed myapp.service，再启动服务。最后检查 systemctl is-active myapp.service 和新日志，并实际执行一次服务对应的请求。
